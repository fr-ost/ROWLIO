Point-and-click selection handles most pages. For the rest, you tell the scraper exactly which elements you want with a selector. There are two languages for this, CSS selectors and XPath. Both are small, and you need only a handful of patterns from each. This article shows those patterns side by side and explains when one is the better choice.

The short answer

Use CSS selectors by default. They are shorter, easier to read and enough for nine cases out of ten. Reach for XPath when you need to select by the text an element contains, move from an element up to its parent, or pull an attribute or a count directly.

The CSS column is shorter almost everywhere. Class matching in particular is clumsy in XPath, because a class attribute can hold several names.

What only XPath can do

Select by text

CSS cannot look at an element's text. XPath can:

//button[contains(., "Load more")]
//th[normalize-space()="Price"]

This is valuable on pages where class names are meaningless but the visible labels are stable.

Walk upwards and sideways

Suppose a page lists specifications as label and value pairs with no useful classes. Find the label, then step to the cell next to it:

//td[normalize-space()="Weight"]/following-sibling::td[1]

Or find a row that contains a particular link and take the whole row:

//a[contains(@href,"/seller/")]/ancestor::tr

Return values, not elements

XPath can return an attribute, a number or a string directly:

//a/@href
count(//article)
string(//h1)

What CSS does better

Modern CSS has caught up in places. The :has() selector picks a parent by its contents, which covers many "walk upwards" cases:

article:has(.badge-sale)
li:not(.ad)

Chrome supports both, and they read more clearly than the XPath equivalents.

Writing selectors that survive a redesign

A selector that works today can fail next month when the site changes its markup. Some choices age better than others.

  • Prefer meaning over position. .product-title will outlive div > div:nth-child(3) > span.
  • Avoid generated class names. Names like css-1x2y3z or sc-bdVaJa are produced by build tools and change with every release.
  • Use stable attributes. data-testid, itemprop, aria-label and rel are there for machines and rarely change.
  • Keep it short. Every extra step is one more thing that can break. Start from the nearest stable ancestor.
  • Anchor on text when classes are useless. Visible labels change less often than markup.

Rows and fields: the pattern for lists

To extract a list, you need two kinds of selector. A row selector matches each record, for example article.product. Field selectors are then evaluated inside each row: h2 for the title, .price for the price, a with its href for the link.

This keeps values together. If one product has no rating, its rating cell is empty and the others stay in the right rows. Selecting all titles and all ratings as two separate lists would silently misalign them.

Test before you run

Never run a selector blind. In Rowlio's Advanced Selectors screen you type a selector and see how many elements match, a sample of their values, and the matches highlighted on the page. Chrome's developer tools do something similar: press Ctrl+F in the Elements panel and type a CSS selector or an XPath expression.

Check two numbers every time: the match count equals the number of items you can see, and no field reports fewer matches than there are rows unless that is expected.

Summary

Learn six CSS patterns and three XPath ones and you can describe almost anything on a page. Start with CSS, switch to XPath for text and for moving around the tree, and always prefer selectors that describe what the element is over where it happens to sit. If you are new to all of this, start with point and click and come back when a page needs more.
